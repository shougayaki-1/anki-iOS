# 達成記録（Issue #102）

## 判定

全デッキ共通。正式なAgain/Hard/Good/EasyのReviewLogだけが根拠となる。ヒント・解答表示・練習・セッション終了は達成を作らない。

- 学習日は設定された開始時刻（既定4:00）から翌日の開始時刻未満。暦の日加算を使い、DSTもStudyDayと同じ境界で扱う。
- 現在の連続日数は今日が未学習なら昨日から数える。今日と昨日が未学習なら0。最長は全保存履歴から復元する。初日・翌日・欠けた日の再開はそれぞれ1・前日+1・1。節目は1/3/7/14/30/100日。
- 日次目標は学習日内のユニークCard UUID数。目標nilは無効。同一カード20評価は1枚。目標変更操作ではイベントを作らない。次の正式評価の保存で現在の目標を満たせば達成できる。同日1回までで、目標達成によって学習キューや回答上限を変更しない。
- 長期定着は現在存在する停止していないCardのReview状態かつ有限のStability >= 21日。`MatureCards.contains`をFSRS統計と達成判定で共有する。デッキの学習一時停止はカード停止とは異なり、推定枚数を変更しない。Note数・想起確率の和ではない。永久記憶の保証ではない。
- 成熟判定は今回のカードが上記条件外から条件内へ移り、全体枚数が10/50/100/500の閾値を超えた正式保存だけが起点。導入時に既に満たす閾値は通知なしのbaselineにする。取り込みだけでは通知しない。次の成熟判定でも評価前に満たす閾値をbaselineにし、過去分を一斉配信しない。

## 永続化・失敗・Undo

既存ExtraPreferencesのStudyOptions JSONに任意の`achievements`と`matureAchievementBaseline`を追加する。テーブル・SwiftDataスキーマ・バックアップ形式バージョンは変更しない。旧JSONはnilとして読める。既存バックアップのoptionsに含めて復元される。ストアの再生成・既存学習データの初期化は行わない。

ReviewLog、FSRS状態、セッション、達成JSONは同じ既存transactionで保存する。保存失敗では全てrollbackし通知しない。コミットと通知の間に終了しても、次回pending APIで保存済みイベントを取得できる。

Undoは評価ログと同じトランザクションで、そのログ起点の未表示イベントを削除する。現在・最長の連続日数とユニーク数は常に現存ReviewLogから再計算する。表示済みイベントは達成時の履歴として残し、再回答でも演出を再生しない。現在値と達成当時の履歴は区別して表示する。

削除済み・停止中カードの過去ReviewLogは日次実績に含める。履歴自体を削除すると実績も減る。未表示イベントは配信時に起点ログ・当時の日次条件・現在の定着枚数を再確認し、条件を満たさないものを除外する。表示済み履歴は現在の実績の保証ではない。

## 日境界変更・旅行・復元

現在の連続記録は現在のCalendar/time zoneと開始時刻で過去のtimestampを再分類する（既存統計と同じ）。変更・画面表示・再起動で新規イベントは生成しない。達成当時の履歴は保存した日付キー・timezone・開始時刻を使い、表示日を後から変えない。

日次イベントIDは暦日キー+種別（目標値変更でも同じID）。streakAdvancedは毎日1件、thresholdは節目の日数、それ以外は0。matureMilestoneは閾値ごとに全期間1件。旅行で同じ暦日へ戻っても表示済み同種イベントを再演出しない。異なる暦日のイベントは区別する。

再インストール後にバックアップを復元すれば履歴・表示済み状態も戻る。古いバックアップやReviewLogのみの復元では連続日数と最長を復元するが、導入前の達成イベントや過去の目標値は推測して生成しない。バックアップにない表示状態は復元できない。

## Issue #103向けAPI

- `achievementProgress(now:)`: 現在の実績。
- `achievementHistory()`: 表示済み履歴と現在も根拠がある未表示履歴。
- `pendingAchievementEvents()`: 型付きAchievementEventの保存済み未表示キュー。再起動・アプリ復帰でも取得できる。
- `Notification.Name.studyAchievementEventsAvailable`: 正式保存成功直後、objectはStudyRepository、userInfo["events"]は[AchievementEvent]。通知自体はメモリ上の案内で、pendingキューが正本。
- `claimAchievementEvent(id:now:)`: 演出を始める直前に呼ぶ。表示済み状態の保存成功時だけイベントを返し、重複ならnil、保存失敗ならthrow。通知の再受信もこのAPIで重複を防ぐ。アプリの単一MainActor repositoryを使用する。

claim直後にプロセスが終了すると演出を見られない場合があるが、二重演出を避ける「高々1回」を優先する。記録画面の閲覧はclaimを行わない。全画面演出は#103で実装する。
