# Issue #12 FSRS-6個人最適化

設定 → FSRS個人最適化 →「履歴から計算・比較」。条件を満たす結果を確認し「この結果を適用」で次回評価から有効にする。「標準設定に戻す」で次回評価から既定値を使う。既存due、カードUUID、FSRS状態、ReviewLog、学習下書き、Undoを適用・撤回時に変更しない。保持率は#7のデッキ設定／継承を引き続き使用する。

## 評価・最小条件

固定Swift-FSRS revision `4fbaf20184d62f82a9f44f343337c61a2c5483e9`、FSRS-6、21個の値、fuzzなし、短期学習あり。採用Swift版には訓練APIがないため、同じライブラリで初回から評価までを再演する。独立した近似FSRS式を使わない。Context7のSwiftUIとTS-FSRSのカスタム値・訓練互換資料、固定Swift版のソースを確認した。TS/Rust/Pythonの最適化器はアプリ実行に利用しない。

計算方法はアプリ独自の限定座標探索 `FSRS-6-coordinate-v1`。公式optimizerと同じ学習器ではなく、収束・大域最適・改善を保証しない。既定値±50%と固定版の有効範囲の共通部分で、相対20%、10%の順に各値を正負方向へ探索する。訓練目的は平均二項Log loss＋既定値への小さな正則化（相対移動二乗和×0.0001）。固定順序で乱数なし。同じ履歴で同じ結果になる。

- 実履歴は日付・sequenceで整列。初回記録がnewのカードだけを採用し、最初の状態が不足する履歴を除外。履歴リセットのnewでは状態を再初期化する。
- 同日や24時間未満の回答は状態再演に含めるが、精度評価には数えない。newも精度評価から除外する。Again=忘却(0)、Hard/Good/Easy=想起(1)。
- 日をまたぐ回答400件、UTC暦日の学習30日、20カード以上が必要。日数は統計・日次枠の学習日とは独立した診断用。すべての履歴の上限は1万件。途中履歴だけの切出しや不完全な系列への置換はしない。
- 有効回答の古い80%に相当する日時までを訓練、以降を検証とする。同時刻を両側に分けないため比率は厳密な80/20とは限らない。訓練320件・検証80件以上、各側にAgainと成功が5件以上必要。
- 検証値は予測してから実回答で次の状態を更新する逐次評価。訓練損失に検証回答を混ぜない。Log lossと非ビン分割RMSE（Brier scoreの平方根）を表示する。
- 検証Log lossが標準値の99%以下、RMSEが標準以下であることを採用条件とする。個人値を既に使用中なら、その値にも両指標で悪化しないことを要求する。結果は改善の保証ではなく、同じ検証期間を繰り返し使う際の選択バイアスも残る。

## 保存と負荷

履歴と適用中設定を値として取得し、utilityの独立Taskで再演する。60秒で中止、各64回答でキャンセルを確認。画面離脱・非active・キャンセルでは設定を変えない。中断計算はチェックポイントとして保存せず、再訪後の明示操作で最初から計算する。計算中の進捗は不定表示。訓練・適用前に履歴SHA-256、件数・日数・分割日時・検証数、前の適用値を確認し、変化があれば再計算を案内する。

結果・有効値・直近20回の適用撤回の日時と前後値・手法をOptionalなStudyOptions JSONへ原子的に保存。既存SwiftDataモデルは変更しない。旧データは標準値。完全バックアップで復元し、不正値・版・数値・日時を検証する。今後の評価ログには固定revisionと実際の21個の値をlibraryLog JSONの追加キーとして記録し、従来のReviewLogデコーダー互換を維持する。個人値使用中の想起確率も同じ値で計算する。

端末内で完結し、履歴の外部送信・AIサービスはない。上限内でも端末や履歴により60秒で中断しうる。その場合は現在の設定を継続する。
